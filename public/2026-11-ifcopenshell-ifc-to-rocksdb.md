# はじめに

IfcOpenShellでIFCファイルをRocksDBに変換できるので、今回はその使い方と中身を調べるよ！

というわけで前の記事で取り上げた[遅延読み込み](https://qiita.com/kiyuka/items/0d2ef739a0d34606a52f)や[SQLiteへの変換](https://qiita.com/kiyuka/items/37c9ec8f4654ec462832)の続き的なものだよ。

なお、この記事では IfcOpenShell 0.9.0.post1 を使用しています。

# 使い方

`convert_path_to_rocksdb()` に入力のIFCファイルと出力先を渡すだけ！

```py
import ifcopenshell

# IFCのパスを渡して変換する
ifcopenshell.convert_path_to_rocksdb("model.ifc", "model.rocksdb")

# 変換したDBを読み取り専用で開く
model = ifcopenshell.open("model.rocksdb", readonly=True)
wall = model.by_type("IfcWall")[0]
print(wall.id(), wall.GlobalId, wall.Name)
```

ちなみに変換後のRocksDBはファイルではなくてディレクトリになるよ。例えば以下のような感じだよ。

```text
model.rocksdb/
├── 000004.log
├── 000008.sst
├── CURRENT
├── IDENTITY
├── LOCK
├── LOG
├── MANIFEST-000005
└── OPTIONS-000007
```

# RocksDBに保存されるデータ形式

:::note info
この節は一見さんお断り領域だよ！見たらだめだよ！スキップ推奨だよ！
:::

そんなわけでIFCファイルのデータがどのような形式でRocksDBに保存されるのかを見ていきます。

まず前提として[RocksDB](https://rocksdb.org/)は、RDBではなくて key-value形式のDBです。そのためSQLiteなどと違って「どういう列を持つか」ではなくて「どういう取得を行うか」で考える必要があります。
たとえば、IfcOpenShellでは `by_id`, `by_type`, `by_guid` などで要素の取得を行います。つまり `#34509` などのIDや`IfcWall`の型などをキーとして持つ形にする必要があるわけですね。

以降は、AC20-FZK-Haus.ifc のデータである以下の`IfcSlab`を例に説明していきます。

```ifc
#34509= IFCSLAB('1pPHnf7cXCpPsNEnQf8_6B',#12,'Bodenplatte',$,$,#34464,#34505,'E4D9CD4B-CA43-4735-94-BD-1FD4376BD455',.BASESLAB.);
```

## インスタンスの属性と型

まずは `by_id` での取得に必要な情報がどのようなデータ形式で登録されているか、についての説明です。

`#34509` のデータには、`IfcSlab`の型と`GlobalId`〜`PredefinedType`の9個の属性の情報があります。これらの情報は以下のようなデータとしてRocksDBに登録されます。

```jsonc
// IfcSlab
{
  "key": "i|00000000000086cd|_",
  "value": "8903000000000000"
}
// GlobalId: 1pPHnf7cXCpPsNEnQf8_6B
{
  "key": "i|00000000000086cd|0000000000000000",
  "value": "47317050486e66376358437050734e456e5166385f3642"
}
// OwnerHistory: #12
{
  "key": "i|00000000000086cd|0000000000000001",
  "value": "4a690c00000000000000"
}
// Name: Bodenplatte
{
  "key": "i|00000000000086cd|0000000000000002",
  "value": "47426f64656e706c61747465"
}
// Description: $
{
  "key": "i|00000000000086cd|0000000000000003",
  "value": "41"
}
// ObjectType: $
{
  "key": "i|00000000000086cd|0000000000000004",
  "value": "41"
}
// ObjectPlacement: #34464
{
  "key": "i|00000000000086cd|0000000000000005",
  "value": "4a69a086000000000000"
}
// Representation: #34505
{
  "key": "i|00000000000086cd|0000000000000006",
  "value": "4a69c986000000000000"
}
// Tag: E4D9CD4B-CA43-4735-94-BD-1FD4376BD455
{
  "key": "i|00000000000086cd|0000000000000007",
  "value": "4745344439434434422d434134332d343733352d39342d42442d314644343337364244343535"
}
// PredefinedType: .BASESLAB.
{
  "key": "i|00000000000086cd|0000000000000008",
  "value": "498d030000000000000300000000000000"
}
```

はい、よくわからないですね。解説します。

`key` の `i|00000000000086cd` については共通になっていることがわかります。これは「ID が `#34509` のデータ」という意味です。`86cd` というのは `34509` を16進数にしたものです。これを0埋めして固定長にしているので`00000000000086cd`になっています。
`|` 区切りの3つ目については `_` はIFCの型を示し、他は属性のindexを示します。

`value` については、たとえば `Name` の value の `47426f64656e706c61747465` は、次のように読めます。

```text
value: 47 | 42 6f 64 65 6e 70 6c 61 74 74 65
       │    └ UTF-8文字列「Bodenplatte」
       └ 文字列を表す識別子 G
```

IFCの値には数値や文字、リストなどいろいろな種類のデータがあるので、最初の文字でデータ型を示し、その後に実際のデータが16進数で入るような形です。文字列であれば識別子を`G`としているので、`Name`の場合は最初に`G`が入りその後に文字列のデータが入る形です。

また、IfcSlabの value: `8903000000000000` ですが、これはリトルエンディアンとして読むので値としては `905`（`0389`は16進数にしたもの）です。IfcOpenShellがIfcSlabに内部番号として905を割り当てているのでこの値が登録されます。

```text
89 03 00 00 00 00 00 00（リトルエンディアン）
└ 16進数：0389、10進数：905
```

<details><summary>識別子一覧</summary>

| 識別子 | hex | 内容 | 値の例 |
| --- | --- | --- | --- |

| `B` | `42` | 派生属性のマーカー | `*` |

| `D` | `44` | BOOLEAN | `.T.` / `.F.` |
| `E` | `45` | LOGICAL | `.T.` / `.F.` / `.U.` |
| `F` | `46` | 実数 | `1.5` |
| `G` | `47` | 文字列 | `'AAA'` |
| `H` | `48` | BINARY 型 | `10110010` |
| `I` | `49` | 列挙値 | `.ELEMENT.` |

## 検索用の索引

次に `by_guid`, `by_type` での検索に必要な情報です。keyの先頭に `guid` は `g`, `type` は `t` が入っています。
guidの方はkeyにGlobalId、valueにIDが16進数で入る形です。typeの方はkeyにIfcSlabの内部番号905、valueにIDのリストが入る形ですね。

```jsonc
// key: GlobalId, value: #34509
{
  "key": "g|1pPHnf7cXCpPsNEnQf8_6B",
  "value": "cd86000000000000"
}
// key: IfcSlab, value: [#34509, #59290, #59553, #59753]
{
  "key": "t|0000000000000389",
  "value": "cd860000000000009ae7000000000000a1e800000000000069e9000000000000"
}
```

`get_inverse` での検索の情報もあります。`#34509`を参照しているデータに何があるか、の検索ですね。こちらはkeyの先頭に`v`が入る形です。

```jsonc
// key: #34509を参照する IfcRelAssociatesMaterial.RelatedObjects, value: #34531
{
  "key": "v|00000000000086cd|000000000000032c|0000000000000004",
  "value": "e3860000"
}
// key: #34509を参照する IfcRelContainedInSpatialStructure.RelatedElements, value: #14517
{
  "key": "v|00000000000086cd|0000000000000337|0000000000000004",
  "value": "b5380000"
}
// key: #34509を参照する IfcRelDefinesByProperties.RelatedObjects, value: #34539 など5件
{
  "key": "v|00000000000086cd|000000000000033e|0000000000000004",
  "value": "eb860000f38600002a8700003587000055870000"
}
// 他...
```

keyはちょっと特殊です。3つの値の組み合わせになっています。たとえば、`IfcRelAssociatesMaterial`を例にすると、最初の `86cd` は参照先であるIfcSlabのID `#34509`、次の `032c` は参照元である `IfcRelAssociatesMaterial` の内部番号`812`、最後の`4`は`RelatedObjects` の属性indexという形式になっています。

```text
v|00000000000086cd|000000000000032c|0000000000000004
    └ 参照先 #34509   └ 参照元の型 812   └ 属性位置 4
```

なお、RocksDBではkeyは完全一致でなくても先頭一致での検索もできます。そのため `get_inverse` の取得はkeyの先頭部分である `v|00000000000086cd|` で検索を行うことで、`#34509`を参照しているIDの一覧の取得を行うことができます。

## ヘッダー

最後にヘッダー情報です。keyの先頭に`h`が入る形です。以下はいくつかの抜粋です。属性と同じ形式ですね。

```jsonc
// implementation_level: 2;1
{
  "key": "h|file_description|0000000000000001",
  "value": "47323b31"
}
// time_stamp: 2016-12-21T17:54:06
{
  "key": "h|file_name|0000000000000001",
  "value": "47323031362d31322d32315431373a35343a3036"
}
// schema_identifiers: ["IFC4"]
{
  "key": "h|file_schema|0000000000000000",
  "value": "4e040000000000000049464334"
}
```

# パフォーマンスの計測

それでは、お楽しみの？処理時間とメモリ使用量の計測です。

計測の詳細については、[計測スクリプト・実行環境](https://github.com/kiyuka829/qiita-articles/tree/dcd0db9da588a3644b83f6988ba055f69b9d76ff/scripts/ifcopenshell-rocksdb) を参照してください。

## RocksDBへの変換

まずは変換にかかる時間、変換後のDB容量、変換時のメモリ使用量です。

| IFCサイズ | 変換時間 | RocksDBサイズ | メモリ増加量 |
| ---: | ---: | ---: | ---: |
| 2.57 MB | 0.262 秒 | 2.00 MB | 34.18 MB |
| 49.67 MB | 4.379 秒 | 26.94 MB | 291.85 MB |
| 97.06 MB | 8.081 秒 | 64.31 MB | 463.67 MB |
| 222.10 MB | 18.653 秒 | 129.09 MB | 874.63 MB |
| 392.86 MB | 38.539 秒 | 252.56 MB | 1,603.65 MB |

RocksDBのサイズは、どれもIFCファイルより小さくなりました。約393 MBのIFCでは、約253 MBになっています。変換時間については純粋にファイルサイズに比例していそうです。

メモリ使用量は...なんか多いですね？以前計測した[遅延読み込み](https://qiita.com/kiyuka/items/0d2ef739a0d34606a52f)よりも多くなっています。単純に考えれば読み込んだデータは随時DBに保存すればいいのでメモリはここまで使用しないはずです。
調べてみたところ、0.9.0.post1ではインスタンスの情報をDBを保存したあとに解放していないようでした。ただ、すでに修正されているようで、次の 0.9.1 のリリースで対応されるようです。そのため、メモリ使用量についてはそちらで改善されていると思われます。

参考：[0.9.0.post1のRocksDB変換処理](https://github.com/IfcOpenShell/IfcOpenShell/blob/ifcopenshell-python-0.9.0post1/src/serializers/rocks_db_serializer.cpp#L101), [メモリ改善PR](https://github.com/IfcOpenShell/IfcOpenShell/pull/9863)

## 開く時間とメモリ使用量

次に、元のIFCを通常・lazyで開く場合と、変換済みのRocksDBを開く場合を比較します。

各列は「開く時間（秒）／メモリ増加量（MB）」です。

| IFCサイズ | IFC 通常 | IFC lazy | RocksDB |
| ---: | ---: | ---: | ---: |
| 2.57 MB | 0.024 秒 / 16.35 MB | 0.009 秒 / 10.34 MB | 0.002 秒 / 1.03 MB |
| 49.67 MB | 0.483 秒 / 235.70 MB | 0.144 秒 / 143.31 MB | 0.002 秒 / 2.36 MB |
| 97.06 MB | 0.842 秒 / 439.78 MB | 0.324 秒 / 234.98 MB | 0.003 秒 / 3.98 MB |
| 222.10 MB | 2.006 秒 / 1,046.58 MB | 0.701 秒 / 559.12 MB | 0.003 秒 / 7.50 MB |
| 392.86 MB | 3.983 秒 / 2,020.10 MB | 1.444 秒 / 1,018.56 MB | 0.003 秒 / 13.43 MB |

開くだけなら、RocksDBはかなり軽くなりました。一番大きいファイルでも、今回の条件では約0.003秒、メモリ増加量は約13 MBです。

## 属性アクセス時間

全インスタンスから最大10万件を無作為に選び、そのインスタンスの全属性を読む処理を2回行いました。一番小さいファイルは全44,249件、残りの4ファイルは各10万件が対象です。

各列は「初回 / 再参照」、単位はマイクロ秒（μs）、1インスタンスに対する属性アクセスの平均です。

| IFCサイズ | IFC 通常 | IFC lazy | RocksDB |
| ---: | ---: | ---: | ---: |
| 2.57 MB | 1.09 / 1.07 | 1.54 / 1.02 | 4.75 / 3.93 |
| 49.67 MB | 1.24 / 1.22 | 5.75 / 1.12 | 6.98 / 4.36 |
| 97.06 MB | 1.69 / 1.65 | 6.98 / 1.54 | 11.17 / 7.39 |
| 222.10 MB | 1.60 / 1.52 | 7.22 / 1.41 | 11.94 / 6.40 |
| 392.86 MB | 1.70 / 1.57 | 7.54 / 1.43 | 13.67 / 6.53 |

属性アクセスは、RocksDBの方が遅くなりました。一番大きいファイルの初回参照では、通常読み込みが約1.70 μs、lazyが約7.54 μs、RocksDBが約13.67 μsです。
再参照はlazyもRocksDBも短くなっていますが、RocksDBは再参照でも通常・lazyより時間がかかっています。

## 属性アクセスで増えるメモリ

最後に、属性を読むときにメモリがどれくらい増えるかを確認します。

以下は10万件のインスタンスの全属性を読んだときのメモリ増加量です。各列は「属性アクセスでの増加量 / 開いてからの合計」です。

| IFCサイズ | IFC lazy | RocksDB |
| ---: | ---: | ---: |
| 49.67 MB | 11.16 / 154.47 MB | 115.88 / 118.24 MB |
| 97.06 MB | 17.45 / 252.43 MB | 205.42 / 209.40 MB |
| 222.10 MB | 15.76 / 574.88 MB | 353.04 / 360.54 MB |
| 392.86 MB | 17.47 / 1,036.03 MB | 489.37 / 502.80 MB |

一番大きいファイルでは、RocksDBを開いてから10万件の属性を読むと、メモリ使用量が約489 MB増えました。開いたときの増加分も合わせると約503 MBです。

なお、一番大きいモデルはインスタンス数が約540万件であり、10万件はその約1.9%なので読んだ割合はまだ少ない状態です。

### 属性アクセスを増やしたときのメモリの増加傾向

RocksDBでの属性アクセス時のメモリ増え過ぎでは？と思ったので調べてみたら[RocksDBのブロックキャッシュの上限](https://github.com/IfcOpenShell/IfcOpenShell/blob/ifcopenshell-python-0.9.0post1/src/ifcparse/file.cpp#L117)を1GBに設定しているようです。IfcOpenShell側のキャッシュに加えてRocksDBのキャッシュも増えるのでメモリが増えることになります。
しかし、逆に言えばRocksDBのブロックキャッシュが上限に近づけば、キャッシュによるメモリ増加は緩やかになるはずです。確認してみましょう。

以下は一番大きい393MBのモデルで属性アクセス数を増やしていったときのメモリ増加量です。各列は「属性アクセスでの増加量 / 開いてからの合計 / 直前の行から10万件あたりの増加量」です。

| 読んだ件数 | IFC lazy | RocksDB |
| ---: | ---: | ---: |
| 10万件 | 17.7 / 1,030.1 / 17.7 MB | 488.4 / 499.7 / 488.4 MB |
| 30万件 | 49.5 / 1,061.9 / 15.9 MB | 792.6 / 803.9 / 152.1 MB |
| 60万件 | 96.9 / 1,109.3 / 15.8 MB | 924.7 / 936.0 / 44.0 MB |
| 100万件 | 159.8 / 1,172.2 / 15.7 MB | 1,013.4 / 1,024.7 / 22.2 MB |
| 200万件 | 319.0 / 1,331.4 / 15.9 MB | 1,180.6 / 1,191.9 / 16.7 MB |
| 300万件 | 477.0 / 1,489.4 / 15.8 MB | 1,308.9 / 1,320.2 / 12.8 MB |

列中の一番右の値が10万件あたりのメモリ増加量です。lazyはおおよそ一定なのに対して、RocksDBは段々と少なくなっており、200万件以降はlazyと同等以下になっていることがわかります。

# まとめ

そんなわけで、RocksDBに変換して速度とかメモリを計測しました。事前に変換しておけるのであれば省メモリで使えそうな気がしますね。特に大きいモデルに対して部分的にアクセスすることが多いのであれば有用な気がします。ただ、属性アクセスは遅いようなので、そこはうまいこと使い分けるっていう感じでしょうか？
