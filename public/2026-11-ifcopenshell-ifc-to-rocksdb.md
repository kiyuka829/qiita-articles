# new article body

- DBへの事前変換には時間とメモリがかかる。
- 変換済みDBを開く処理は速く、初期メモリも少ない。
- 属性アクセスは、通常・lazyより遅い。
- アクセスを進めると、メモリ使用量も増える。
- 変換済みDBを再利用し、必要な部分だけ読む用途では、特にメモリ面で有利。

## 属性の読み方

そこは説明が紛らわしかったです。**どちらもRocksDBを読む場合の話**です。

```py
model = ifcopenshell.open("model.rocksdb", readonly=True)

# 通常のモデルAPI：IFCを開いたときと同じ操作方法
model.by_id(389).Name

# storage経由：内部のストレージへ直接アクセス
model.storage.by_id(389).Name
```

前者は、保存形式がIFCでもRocksDBでも使う共通のAPIです。

- **通常のAPI**：共通の内部インスタンスとして扱うので、既存のIfcOpenShellの処理につなげられます。取得したインスタンスはC++側のキャッシュに保持されます。
- **`storage` 経由**：その内部インスタンスを作らずに取得します。ただし、`storage.by_id()` はPythonの専用オブジェクトを作り、型名・属性数などをキャッシュします。RocksDB自身のブロックキャッシュも利用します。

さらに生データ寄りの `storage.read(key)` なら、保存されたバイト列をそのまま取得できます。

なので、正確には **「共通の内部インスタンスとして保持する処理を避けられる。ただし、別のキャッシュや取得データのメモリは使う」** という違いです。

`storage.by_id()` はなんかよくわからないけど使い物にならないもの。なのでstorageの話は書かなくていい。

## バグ

今回の **IfcOpenShell 0.9.0.post1** の検証では、次の差がありました。

| 対象 | 通常のモデルAPI（RocksDB） | `storage` 経由 |
| --- | --- | --- |
| `#389.RefLatitude` | 正しい `(49, 6, 1, 566000)` | `(49, 0, 6, 0, 1, 0, 566000, 0)` |
| `#77.NominalValue` の中の値 | 正しく取得できる | 取得時に `unpack requires a buffer of 4 bytes` |

調査メモでは、**C++が8バイトで保存した整数を、Python側の復元処理が4バイトとして読む違い**で説明できると整理されています。

精度が落ちたりするという話ではなくて落ちる。

- **整数単体**：想定するバイト数と合わず、例外で処理が止まります。
- **整数配列**：例外にならず、余分な `0` が混ざった誤った配列を返します。

数値の丸めや精度の問題ではなく、保存されたバイト列の読み解き方が誤っている問題です。

また、`UNKNOWN` が `False` になる問題もありますが、これは**通常のモデルAPIでも `storage` 経由でも発生**しています。保存済みデータの時点で `False` になっているため、別の問題です。

## DBに保存されるデータ

```json
{
  "key": "i|0000000000000185|0000000000000002",
  "value_hex": "4747656c61656e6465",
}
```

はい、その理解で合っています。**値の先頭1バイトは型識別子**なので、そこだけ補足です。

```text
i | 0000000000000185 | 0000000000000002
│   │                  └ 属性位置：2（0始まり。この場合はName）
│   └ インスタンスID：0x185 = 389
└ インスタンスのデータを格納するキー
```

`i` はインスタンス用の領域を示し、`by_id(389)` で取得する対象に対応しています。

値はこう分かれます。

```text
47 | 47 65 6c 61 65 6e 64 65
│    └ UTF-8でデコードすると "Gelaende"
└ 文字列であることを示す識別子（ASCIIの G）
```

つまり、**「#389 の属性位置2には、文字列 `Gelaende` が保存されている」**というレコードです。

先頭の識別子まで文字としてデコードすると `GGelaende` になるので、先頭1バイトを取り除いてから文字列にします。

---

| 検索 | API | DBのキー |
| --- | --- | --- |
| ID → インスタンス | `by_id()` | `i \| ...` |
| GlobalId → インスタンス | `by_guid()` \| `g | ...` |
| 型 → インスタンス一覧 | `by_type()` | `t \| ...` |
| 参照先 → 参照元の一覧 | `get_inverse()` | `v \| ...` |

- `i|`：インスタンスの属性・型
- `g|`：GlobalIdの索引
- `t|`：型別の索引、または型付き値の属性・型
- `v|`：逆参照の索引
- `h|`：IFCヘッダー

### i

| キー | value |
| --- | --- |
| `i \| instance_id \| attribute_index` | 属性の型識別子 ＋ 属性値のバイナリ |
| `i \| instance_id \| _` | IFCの型を表す、スキーマ内の番号 |

```text
key:
i|0000000000000185|_

value（hex）:
85 03 00 00 00 00 00 00
└ 整数901 → 今回のIFC4スキーマでは IfcSite
```

| 属性値の種類 | valueの構成 |
| --- | --- |
| 未設定 `$` | `A` の1バイトだけ |
| 整数 | `C` ＋ 8バイト整数 |
| 実数 | `F` ＋ 8バイト浮動小数点数 |
| 文字列 | `G` ＋ UTF-8のバイト列 |
| インスタンス参照 | `J` ＋ `i` ＋ 参照先ID |
| 型付き値への参照（`IfcLengthMeasure(1.5)` など） | `J` ＋ `t` ＋ 内部番号 |
| 参照の配列 | `P` ＋「参照の種類・番号」の繰り返し |

| 例 | 値 | 保存時の識別子 |
| --- | --- | --- |
| `IfcSite.RefLatitude` | `(49, 6, 1, 566000)` | `L`：整数の配列 |
| `IfcCartesianPoint.Coordinates` | `(0.0, 1.0, 2.0)` | `M`：実数の配列 |
| `IfcRelAggregates.RelatedObjects` | `(#434, #435)` | `P`：参照の配列 |
| `IfcPropertyListValue.ListValues` | `(IfcLabel('AAA'), IfcLabel('BBB'))` | `P`：型付き値への参照の配列 |

| 識別子 | hex | 内容 | 値の例 |
| --- | --- | --- | --- |
| `A` | `41` | 未設定 | `$` |
| `B` | `42` | 派生属性のマーカー | `*` |
| `C` | `43` | 整数 | `123` |
| `D` | `44` | BOOLEAN | `.T.` / `.F.` |
| `E` | `45` | LOGICAL | `.T.` / `.F.` / `.U.` |
| `F` | `46` | 実数 | `1.5` |
| `G` | `47` | 文字列 | `'AAA'` |
| `H` | `48` | BINARY 型 | `10110010` |
| `I` | `49` | 列挙値 | `.ELEMENT.` |
| `J` | `4a` | インスタンス・型付き値への参照 | `#389` / `IfcLabel('AAA')` |
| `K` | `4b` | 空の集約 | `()` |
| `L` | `4c` | 整数の配列 | `(1, 2, 3)` |
| `M` | `4d` | 実数の配列 | `(1.0, 2.0, 3.0)` |
| `N` | `4e` | 文字列の配列 | `('AAA', 'BBB')` |
| `O` | `4f` | BINARY 型の配列 | ビット列の一覧 |
| `P` | `50` | 参照の配列 | `(#389, #434)`、型付き値の一覧 |
| `Q` | `51` | 空の2次元集約 | 空の入れ子の集約を表すマーカー |
| `R` | `52` | 整数の2次元配列 | `((1, 2), (3, 4))` |
| `S` | `53` | 実数の2次元配列 | `((1.0, 2.0), (3.0, 4.0))` |
| `T` | `54` | 参照の2次元配列 | `((#1, #2), (#3, #4))` |

### g

| キー | value |
| --- | --- |
| `g \| GlobalId` | 対応するインスタンスID |

```text
key:
g|0KMpiAlnb52RgQuM1CwVfd

value（hex）:
85 01 00 00 00 00 00 00
└ 389
```

整数を下位のバイトから順に並べています。たとえば次のようになります。

```text
ID      value（hex）
389     85 01 00 00 00 00 00 00
390     86 01 00 00 00 00 00 00
65536   00 00 01 00 00 00 00 00
```

`389` は16進数で `0185` なので、下位の `85`、上位の `01` の順に並び、残りは `00` で埋まっています。

### t

`t|` は、**型別のインスタンス一覧**と、**型付き値の保存**に使われます。キーは次の3パターンです。

| キー | value | 用途 |
| --- | --- | --- |
| `t\|型の番号` | インスタンスIDの一覧 | `by_type()` 用の索引 |
| `t\|内部番号\|_` | 型付き値の型番号 | `IfcLabel` など、型付き値の型を調べる |
| `t\|内部番号\|属性位置` | 型識別子＋属性値 | 型付き値の中身を読む |

数値部分は、これまでと同じく16桁の16進数です。ただし、**型の番号と内部番号は、どちらもIFCのインスタンスIDではありません。**

たとえば、型別索引の実データは次のようになっています。

```text
key:
t|000000000000031d

value:
[400, 436, 481, 20914, 76217]
```

`031d` は、今回のIFC4スキーマで `IfcRelAggregates` を表す番号 `797` です。valueには、その型のインスタンスIDが並びます。実際のvalueは、各IDを8バイトの整数にしたバイナリです。

型付き値の例は、`#77` の `NominalValue = IfcTimeStamp(9685146)` です。この値には内部番号 `53` が割り当てられ、次の2レコードに保存されています。

```text
key:
t|0000000000000035|_

value（hex）:
3c 04 00 00 00 00 00 00
└ 型番号1084 → IfcTimeStamp
```

```text
key:
t|0000000000000035|0000000000000000

value（hex）:
43 | 9a c8 93 00 00 00 00 00
│    └ 整数 9685146
└ 整数を表す識別子 C
```

元の `#77.NominalValue` の属性valueには、この型付き値への参照が入っています。

```text
4a | 74 | 35 00 00 00 00 00 00 00
│    │    └ 内部番号53
│    └ t：型付き値への参照
└ J：参照を表す識別子
```

このように、`i|` の属性から `t|` の型情報と値をたどる形です。

---

- **`t|型の番号`**：たとえば `IfcWall` のインスタンスIDの一覧です。`by_type()` でサブタイプも含める場合は、それぞれの型の一覧を取得します。
- **`t|内部番号|_`**：型付き値に内部番号を付け、その番号から型を調べるためのものです。`IfcTimeStamp(9685146)` にはIFC上の `#123` のようなIDはありませんが、保存時に内部番号を使います。
- **`t|内部番号|属性位置`**：型付き値の中身です。この例では `9685146` です。

`IfcTimeStamp(9685146)` を例にすると、こうです。

```text
t|内部番号53|_ → IfcTimeStamp
t|内部番号53|0 → 9685146
```

実際の型情報のvalueには、`IfcTimeStamp` という文字列ではなく、スキーマ内の型番号が入ります。

### v

`v|` は**逆参照**、つまり「そのインスタンスを参照しているインスタンス」を調べるための索引です。

キーは1パターンです。

| キー | value |
| --- | --- |
| `v\|参照先ID\|参照元の型番号\|参照元の属性位置` | 参照元のインスタンスIDの一覧 |

たとえば、次のIFCデータがあります。

```text
#436=IFCRELAGGREGATES(..., #389, (#434));
```

`#436` の属性位置 `4` は `RelatingObject` で、`#389` を参照しています。この逆参照は、DBに次のように保存されています。

```text
key:
v|0000000000000185|000000000000031d|0000000000000004
  └ 参照先ID 389   └ 参照元の型 797   └ 属性位置 4

value（hex）:
b4 01 00 00
└ 参照元ID 436
```

`797` は今回のIFC4スキーマでの `IfcRelAggregates` の型番号です。つまり、このレコードは次の意味です。

```text
#389 を、IfcRelAggregates の属性位置4から参照している
インスタンス → [#436]
```

同じ条件で参照しているインスタンスが複数ある場合は、valueにIDが続けて入ります。今回の環境では、各IDを**4バイトの整数**として保存しています。

### h

`h|` は、IFCファイルの **HEADERセクション**の情報を保存するためのキーです。

キーは1パターンです。

| キー | value |
| --- | --- |
| `h\|ヘッダー名\|属性位置` | 型識別子＋属性値 |

ヘッダー名には、`file_description`、`file_name`、`file_schema` があります。属性位置は0始まりの16桁の16進数です。

たとえば、IFCスキーマ名を保存した実データは次のようになっています。

```text
key:
h|file_schema|0000000000000000
  └ ヘッダー名 └ 属性位置 0
```

```text
value（hex）:
4e | 04 00 00 00 00 00 00 00 | 49 46 43 34
│    │                         └ "IFC4"
│    └ 文字列の長さ：4バイト
└ N：文字列の配列
```

つまり、復元すると次の値です。

```py
["IFC4"]
```

`N` は以前の一覧にあった「文字列の配列」の識別子です。要素が1件でも配列として保存されています。今回の環境では、各文字列の前にそのバイト長が8バイト整数で入ります。

ほかにも、たとえば `file_name` の属性位置 `1` に作成日時が保存されています。

```text
key:
h|file_name|0000000000000001

value:
G + "2016-12-21T17:54:06"
```

こちらは1つの文字列なので、識別子は `G` です。
