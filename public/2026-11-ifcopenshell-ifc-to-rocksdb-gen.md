# はじめに

前回は [IfcOpenShellでIFCファイルをSQLiteに変換する](https://qiita.com/kiyuka/items/37c9ec8f4654ec462832) 方法を調べたよ！今回はRocksDBに変換するぞ！

[遅延読み込みの記事](https://qiita.com/kiyuka/items/0d2ef739a0d34606a52f) では、`lazy=True` にしても、ファイルを開いた時点でそれなりにメモリを使うことが分かりました。SQLiteに変換してIfcOpenShellで開く場合も、思っていたほど省メモリにはなりませんでした。

ではRocksDBに変換した場合はどうなるのか。実際に変換して、開く時間や属性アクセスの時間、メモリ使用量を確認してみます。

なお、この記事では IfcOpenShell 0.9.0.post1 を使用しています。

# RocksDBへの変換方法

変換には、`ifcopenshell.convert_path_to_rocksdb()` を使います。入力のIFCファイルと、出力先のパスを指定するだけです。

```py
import ifcopenshell

ifcopenshell.convert_path_to_rocksdb(
    "model.ifc",
    "model.rocksdb",
)
```

この関数にはIFCファイルのパスを渡すので、事前に `ifcopenshell.open()` でモデルを読み込む必要はありません。

ここでは `model.rocksdb` という名前にしていますが、出力されるのは1つのファイルではなくディレクトリです。変換先には、まだ存在しないディレクトリのパスを指定します。変換後のDBをコピーするときも、ディレクトリごと扱います。

参考：[変換APIの実装](https://github.com/IfcOpenShell/IfcOpenShell/blob/2744f8426bdef98a486406628a121298a5479690/src/ifcopenshell-python/ifcopenshell/__init__.py#L402)

# 変換したDBを開く

変換後は、いつもの `ifcopenshell.open()` で開けます。今回は読み取り専用にするため `readonly=True` を指定しています。

```py
import ifcopenshell

model = ifcopenshell.open("model.rocksdb", readonly=True)
wall = model.by_type("IfcWall")[0]

print(wall.id(), wall.GlobalId, wall.Name)
```

`by_id()` や `by_type()` でインスタンスを取得し、`Name` などの属性を読む形で使えます。今回のサンプルと計測は、この通常のモデルAPIを使っています。

参考：[読み込みAPIの実装](https://github.com/IfcOpenShell/IfcOpenShell/blob/2744f8426bdef98a486406628a121298a5479690/src/ifcopenshell-python/ifcopenshell/__init__.py#L175)

# 変換・読み込みの時間とメモリ使用量

使い方は簡単でした。ここからは、実際にどれくらい時間とメモリが必要になるかを見ていきます。

前回と同じ5種類のIFCファイルを使い、通常読み込み・遅延読み込み・変換済みRocksDBを比較しました。今回はすべて IfcOpenShell 0.9.0.post1 で計測し直しています。

計測環境は Apple M5・16 GB、macOS 26.6.2、Python 3.12.13。時間とメモリは各条件を別プロセスで3回実行した中央値、容量の単位はMB（1 MB = 1,000,000バイト）です。

メモリはmacOSのphysical footprintを使い、処理前からどれくらい増えたかを示します。基準値はimportと比較用データの準備後に取得しています。最大モデルの変換時には圧縮・スワップも発生しているため、RSSだけでの比較にはしていません。

また、各実行前に入力IFCとDBを順番に読み、OSのファイルキャッシュを温めています。キャッシュが空の状態での測定ではありません。

参考：[計測スクリプト・実行環境](https://github.com/kiyuka829/qiita-articles/tree/dcd0db9da588a3644b83f6988ba055f69b9d76ff/scripts/ifcopenshell-rocksdb)

## RocksDBへの変換

まずは変換にかかる時間、変換後のDB容量、変換時のメモリ使用量です。

変換時間は `convert_path_to_rocksdb()` の呼び出し全体です。DB容量は1回目の変換プロセス終了後の値を載せています。
観測ピーク増加量は、約0.5秒間隔で取得したメモリ使用量と、変換前後の値の最大から基準値を引いたものです。短いピークは見逃している可能性があります。

| IFCサイズ | 変換時間 | RocksDBサイズ | 変換時の観測ピーク増加量 |
| ---: | ---: | ---: | ---: |
| 2.57 MB | 0.262 秒 | 2.00 MB | 34.18 MB |
| 49.67 MB | 4.379 秒 | 26.94 MB | 291.85 MB |
| 97.06 MB | 8.081 秒 | 64.31 MB | 463.67 MB |
| 222.10 MB | 18.653 秒 | 129.09 MB | 874.63 MB |
| 392.86 MB | 38.539 秒 | 252.56 MB | 1,603.65 MB |

今回の5ファイルでは、どれも変換後のDB容量が元のIFCより小さくなりました。約393 MBのIFCでは、約253 MBになっています。

一方で、変換には時間もメモリも必要です。一番大きいファイルでは約38.5秒かかり、メモリも観測ピークで約1.6 GB増えています。

この変換は、後でDBを開くときとは別に必要になる処理です。読み込みが速くなるとしても、最初に変換するコストは考えておきたいところですね。

## 開く時間とメモリ使用量

次に、元のIFCを通常・lazyで開く場合と、変換済みのRocksDBを開く場合を比較します。

各セルは「開く時間（秒）／メモリ増加量（MB）」です。時間はimportを除いた `open()` の実時間、メモリは開く直前と直後の差分です。DBへの変換時間や、属性を読む時間は含みません。

| IFCサイズ | IFC 通常 | IFC lazy | RocksDB |
| ---: | ---: | ---: | ---: |
| 2.57 MB | 0.024 秒 / 16.35 MB | 0.009 秒 / 10.34 MB | 0.002 秒 / 1.03 MB |
| 49.67 MB | 0.483 秒 / 235.70 MB | 0.144 秒 / 143.31 MB | 0.002 秒 / 2.36 MB |
| 97.06 MB | 0.842 秒 / 439.78 MB | 0.324 秒 / 234.98 MB | 0.003 秒 / 3.98 MB |
| 222.10 MB | 2.006 秒 / 1,046.58 MB | 0.701 秒 / 559.12 MB | 0.003 秒 / 7.50 MB |
| 392.86 MB | 3.983 秒 / 2,020.10 MB | 1.444 秒 / 1,018.56 MB | 0.003 秒 / 13.43 MB |

開くだけなら、RocksDBはかなり軽くなりました。一番大きいファイルでも、今回の条件では約0.003秒、メモリ増加量は約13 MBです。lazyの約1秒半・約1 GBと比べても、大きな差があります。

ただし、ここで測っているのはモデルを開いたところまでです。実際に使うときには属性も読むので、その時間とメモリも確認します。

## 属性アクセス時間

全インスタンスから最大10万件を無作為に選び、そのインスタンスの全属性を読む処理を2回行いました。対象のIDは各方式で同じです。参照先のインスタンスの属性までは再帰的に読みません。

一番小さいファイルは全44,249件、残りの4ファイルは10万件だけが対象です。**大きいモデルの全インスタンスを読み切る検証ではありません。**

各セルは「初回 / 再参照」、単位は秒です。モデルを開く時間は含みません。また、取得した値を正規化し、ハッシュを計算して照合する処理も時間に含めています。

| IFCサイズ | 参照件数 | IFC 通常 | IFC lazy | RocksDB |
| ---: | ---: | ---: | ---: | ---: |
| 2.57 MB | 44,249 | 0.195 / 0.192 | 0.219 / 0.192 | 0.373 / 0.334 |
| 49.67 MB | 100,000 | 0.443 / 0.442 | 0.879 / 0.434 | 1.020 / 0.762 |
| 97.06 MB | 100,000 | 0.534 / 0.537 | 1.015 / 0.525 | 1.468 / 1.109 |
| 222.10 MB | 100,000 | 0.524 / 0.521 | 1.040 / 0.507 | 1.564 / 1.032 |
| 392.86 MB | 100,000 | 0.544 / 0.535 | 1.163 / 0.522 | 1.844 / 1.134 |

属性アクセスは、今回の条件ではRocksDBの方が遅くなりました。一番大きいファイルの初回参照では、通常読み込みが約0.54秒、lazyが約1.16秒、RocksDBが約1.84秒です。

2回目はlazyもRocksDBも短くなっていますが、RocksDBは再参照でも通常・lazyより時間がかかっています。

モデルを開くときの速さと、開いた後に属性を読む速さは、分けて考える必要がありそうです。

## 属性アクセスで増えるメモリ

最後に、属性を読むときにメモリがどれくらい増えるかを確認します。

以下は、各実行内で「対象の全属性を読んだ後 − モデルを開いた直後」を計算した結果です。単位はMB、対象件数は上の表と同じです。取得結果をPythonのリストなどに蓄積する処理はしていません。

| IFCサイズ | IFC 通常 | IFC lazy | RocksDB |
| ---: | ---: | ---: | ---: |
| 2.57 MB | 0.85 | 5.95 | 11.49 |
| 49.67 MB | 0.46 | 11.16 | 115.88 |
| 97.06 MB | 1.39 | 17.45 | 205.42 |
| 222.10 MB | 0.72 | 15.76 | 353.04 |
| 392.86 MB | 1.41 | 17.47 | 489.37 |

RocksDBも、使っていくとメモリ使用量は増えます。一番大きいファイルでは、10万件の属性を読んだ後に約489 MB増えました。その時点での、モデルを開く前からのメモリ増加量は約503 MBです。

lazyの増加が小さく見えますが、こちらも増えています。大きいモデルでは10万件が全約540万件の約1.9%なので、読んだ割合はまだ少ない状態です。一方、小さいモデルでは全44,249件を読んで、約5.95 MB増えています。

開く前からの増加量で比べると、大きい4ファイルは10万件の全属性を読んだ後もRocksDBの方が少ない結果でした。ただ、さらに読み進めた場合の使用量は今回の結果だけでは分かりません。

# 取得値の一致について

速度やメモリとは別に、取得した値も比較しています。

今回の IfcOpenShell 0.9.0.post1 では、一部のLOGICAL値で `UNKNOWN` が `False` に変わる差を確認しました。小さいモデルで4件、一番大きいモデルの10万件の標本で3件あり、それぞれ3回の実行で再現しています。

以降のバージョンでの修正状況は確認していませんが、少なくとも今回の結果は「取得値がすべて元のIFCと一致した」というものではありません。上の性能計測は、この差を記録したうえで継続した結果です。

# まとめ

そんなわけで、IfcOpenShellでIFCをRocksDBに変換して、読み込み時間とメモリ使用量を確認しました。

変換済みのDBを開く処理は速く、初期メモリも大きく減りました。一方で、DBを作るための時間とメモリが必要で、属性アクセスは今回の条件では通常・lazyより遅くなっています。使っていくうちにメモリが増えることも確認できました。

毎回IFCを変換してすべてのデータを読む使い方より、事前に変換したDBを再利用し、必要な部分だけ読む使い方が合いそうです。特に、モデルを開いたときのメモリ消費を抑えたい場合には、選択肢になりそうですね。
