# はじめに

IfcOpenShell の `open()` には、属性を必要になったときに読み込む `lazy=True` というオプションがあります。

大きいIFCファイルを扱うときにメモリを節約できそうでうれしいのですが、「必要になったときに読み込む」とは、内部的には何をしているのでしょうか。
ファイルを開いた時点では何を持っていて、属性にアクセスすると何が起こるのか。ソースコードを追いながら整理してみます。

そのうえで、仕組みから予想できるメモリ使用量と処理時間について考えます。

:::note info
この記事は草稿です。内部処理はコミット [`a298d3489419a06636c5f4b423b2fc9c1ceb7c65`](https://github.com/IfcOpenShell/IfcOpenShell/tree/a298d3489419a06636c5f4b423b2fc9c1ceb7c65) のソースを参照しています。
対象は通常のSTEPテキスト形式の `.ifc` を `lazy=True` で開く場合です。実測結果は未記入で、メモリの数値は明記した仮定に基づく概算です。
:::

# まずは全体像

使い方は、`open()` に `lazy=True` を渡すだけです。

```py
import ifcopenshell

model = ifcopenshell.open("model.ifc", lazy=True)
walls = model.by_type("IfcWall")
if walls:
    name = walls[0].Name
```

このときの処理は、大きく次の2段階に分かれます。

```text
open() 時
  ファイル全体を走査する
    → 各インスタンスのID・型・属性の開始位置などを記録する
    → 検索用の索引を作る
    → 各インスタンスの内部オブジェクトを作る

属性に初めてアクセスしたとき
  記録しておいた位置に移動する
    → 対象インスタンスの属性一式をパースする
    → 結果を内部オブジェクトに保持する
```

つまり、**最初にファイル全体を走査して検索の準備を済ませ、属性値のパースと保持を後回しにする**仕組みです。

ファイル全体を走査する処理は `index_lazily()`、後から属性をパースする処理は `materialize()` にあります。[実装はこちら](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/parse.cpp#L2752-L2886)。

# ファイルを開いたときにすること

## インスタンスのIDと型を読む

IFCファイルには、次のような形式でインスタンスが記述されています。

```text
#123=IFCWALL('0123456789012345678901',#5,'Wall A',$,$,$,$,$,$);
```

`#123` がインスタンスのID、`IFCWALL` が型、その後の括弧の中が属性の並びです。

lazy読み込みでも、IDと型は最初に読みます。そして、それぞれのインスタンスに対応するC++の内部オブジェクト `instance_data` を作ります。

この時点では属性の格納領域 `storage_` が空になっています。IDと型は分かるけれど、属性一式をパースした結果はまだ持っていない、という状態です。

| メンバー | 内容 | 初期走査直後 |
| --- | --- | --- |
| `file_` | 所属するモデルへのポインタ | 設定済み |
| `declaration_` | 型定義へのポインタ | 設定済み |
| `identity_` | 内部管理用の識別番号 | 設定済み |
| `id_` | STEPのインスタンスID | `123` |
| `storage_` | パース済み属性の格納領域 | 空 |

型定義はポインタで参照しています。各インスタンスが `IfcWall` の型定義そのものを複製するわけではありません。[`instance_data` の定義](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/instance_data.h#L539-L568)。

## 属性の中も走査して索引を作る

属性値のパースを後回しにするといっても、括弧の中を丸ごと飛ばすわけではありません。

たとえば先ほどの `#123` は、属性の中で `#5` を参照しています。この参照関係を最初に記録しておけば、「`#5` を参照しているのは誰か」を検索できます。

そのため、初期走査では属性の中も読み進め、参照先のIDや、その参照が何番目の属性に現れたかを記録します。

ここでポイントになるのが、括弧の深さです。
IFCの属性にはリストもあるので、カンマが現れたからといって、必ず次の属性に進むわけではありません。実装では括弧の深さを数え、最も外側の属性リストにあるカンマだけで属性番号を進めています。

文字列中の記号などは字句解析器が扱います。そのうえで `attribute_consumer` が括弧・カンマ・参照を受け取り、通常の数値への変換やリストの構築を省きながら索引を作る、という分担です。[`attribute_consumer` の実装](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/parse.cpp#L2631-L2724)。

また、`IfcRoot` を継承するインスタンスについては、先頭属性の文字列をGlobalIdとして取得し、索引へ登録します。[GlobalIdの登録処理](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/parse.cpp#L2853-L2868)。

初期走査で作られる主な索引を整理すると、次のようになります。

| 索引 | 実装名 | 記録する対応関係 |
| --- | --- | --- |
| ID | `byid_` | ID → 内部オブジェクト |
| 型 | `bytype_excl_` | 型 → その型のインスタンス一覧 |
| GlobalId | `byguid_` | GlobalId → インスタンス |
| 逆参照 | `byref_excl_` | 参照先ID → 参照元ID・型・属性番号 |
| 属性の位置 | `lazy_offsets_` | ID → ファイル内の属性開始位置 |

「属性をパースしない」というより、**検索に必要な情報を先に取り出し、通常の属性データとして組み立てる処理を後回しにしている**と捉えると分かりやすそうです。

## 後から戻れるように位置を記録する

後から属性を読むには、ファイルのどこに戻ればよいかが必要です。
そのために使うのが `lazy_offsets_` です。

```text
#123=IFCWALL('0123456789012345678901',#5,'Wall A',$,$,$,$,$,$);
            ↑
            属性の開始位置を記録する
```

位置はインスタンス自身ではなく、モデル側の配列に `(ID, バイト位置)` の組として保持します。

```text
モデル
 ├─ ID索引
 │    123 → instance_data
 │            ├─ 型定義 → IfcWall
 │            ├─ ID = 123
 │            └─ storage_ = 空
 │
 └─ lazy_offsets_
      [(123, 属性開始位置), (124, 属性開始位置), ...]
```

初期走査が終わると、この配列をID順にソートします。逆参照の索引や型別の一覧についてもソートが行われます。[初期走査の末尾](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/parse.cpp#L2881-L2886)。

# 属性にアクセスしたときにすること

## IDからファイル位置を探す

たとえば、先ほど取得した壁の `Name` にアクセスしたとします。

属性を取得する処理では、まず `ensure_loaded()` が呼ばれます。すでに `storage_` があれば、そのまま保持している属性を使います。空であれば `materialize()` が呼ばれ、属性を読み込みます。

`materialize()` は、対象インスタンスのIDを使って `lazy_offsets_` を二分探索します。実装では `std::lower_bound()` が使われています。位置が見つかったら、入力の読み取り位置をそこへ移動し、属性をパースします。[`ensure_loaded()` と `materialize()`](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/parse.cpp#L2741-L2774)。

## パースする単位はインスタンス

ここで読み込まれるのは、要求された `Name` だけではありません。
**そのインスタンスの属性一式をパースして、`storage_` に保持します。**

```text
初期状態
  #123 の storage_ = 空

Name に初めてアクセス
  #123 の属性一式をパース
    → storage_ に保持
    → その中から Name を返す

続けて Description にアクセス
  保持済みの storage_ から取得
```

また、属性中の `#5` のような参照は、対応するインスタンスへの参照として解決されます。ただし、参照先の存在を解決することと、その参照先の属性までパースすることは別です。

なお、逆参照は初期走査で登録しているので、この段階では重複して登録しないようにしています。[属性のパース・保持・参照解決の処理](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/parse.cpp#L2760-L2773)。

# 元ファイルはどれくらいメモリに載せるのか

ここまでの話は、パースした属性データの持ち方でした。もう一つ、入力ファイルのバイト列をどれくらい保持するか、という話があります。

このlazy読み込みでは、ファイルを64 KiBのページ単位で読み込み、最大64ページをキャッシュします。ページ内のデータ部分で計算すると、次のサイズです。

```text
64 KiB × 64ページ = 4 MiB
```

必要なページがキャッシュになければファイルから読み込み、上限に達していればLRU方式でページを入れ替えます。[ページサイズの指定](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/parse.cpp#L2728-L2733)、[ページ取得と入れ替えの実装](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/file_reader.cpp#L166-L214)。

ただし、これは入力ページのデータ部分の容量です。索引や内部オブジェクト、パース済み属性は別にメモリを使います。また、OSのファイルキャッシュとも別の話です。

整理すると、2種類の保持領域があります。

| 保持するもの | 扱い |
| --- | --- |
| 入力ファイルのページ | 上限を設けて入れ替える |
| パース済みの属性 | 各インスタンスの `storage_` に保持し、再利用する |

入力ページが入れ替わっても、すでにパースした属性が一緒に破棄されるわけではありません。属性を読む対象が増えれば、その分の属性データがメモリ上に蓄積していきます。

# メモリ使用量を考える

## 属性を読まなくても必要なメモリがある

open直後のメモリは、大まかには次のように分けられます。

```text
初期状態のメモリ
  ≒ 入力ページ
    ＋ 全インスタンスの内部オブジェクト
    ＋ ID・型・GlobalId・逆参照の索引
    ＋ 属性開始位置の配列
    ＋ その他の管理領域

属性アクセス後のメモリ
  ≒ 初期状態のメモリ
    ＋ アクセスしたインスタンスのパース済み属性
```

そのため、属性をほとんど読まない場合でも、インスタンス数や参照数が多ければ相応のメモリが必要になります。

## 内部オブジェクトと位置情報の概算

64 bit環境を仮定すると、`instance_data` 本体は次のように概算できます。

| メンバー | 仮定するサイズ |
| --- | ---: |
| 所属モデルへのポインタ `file_` | 8バイト |
| 型定義へのポインタ `declaration_` | 8バイト |
| 内部識別番号 `identity_` | 4バイト |
| STEPのID `id_` | 4バイト |
| `storage_` | 16バイト |
| 合計 | 40バイト |

`storage_` は、属性領域へのポインタを持つ構造を `std::optional` で包んだものです。ここでは、ポインタが8バイト、optionalの状態とパディングを含めて16バイトと仮定しています。空のときにもこのメンバーの領域はありますが、属性値を格納する配列はまだ確保しません。[オブジェクトの定義](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/instance_data.h#L539-L568)、[属性格納構造の定義](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/variant_array.h)。

さらに `lazy_offsets_` の1要素は、32 bitのIDと64 bitの位置の組です。アラインメントを含めて16バイトと仮定すると、内部オブジェクトと位置情報だけで1件あたり56バイトになります。

| インスタンス数 | 内部オブジェクト40バイト | 位置情報16バイト | 合計 |
| --- | ---: | ---: | ---: |
| 100万件 | 40 MB | 16 MB | 56 MB |
| 1,000万件 | 400 MB | 160 MB | 560 MB |
| 2,000万件 | 800 MB | 320 MB | 1.12 GB |

単位は10進です。この表には、IDなどの索引、ポインタの管理領域、配列の余剰容量、メモリアロケータの管理領域などは含めていません。実環境の `sizeof` やプロセスのメモリ使用量を測った値でもありません。

## 逆参照の索引は参照数に応じて増える

逆参照のレコードには、次の情報を持ちます。

| 情報 | フィールドのサイズ |
| --- | ---: |
| 参照先ID | 4バイト |
| 参照元ID | 4バイト |
| 参照元の型番号 | 2バイト |
| 属性番号 | 2バイト |
| 合計 | 12バイト |

こちらはインスタンス数ではなく、属性中に現れる参照の数に応じて増えます。[`inverse_record` の定義](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/storage.h#L150-L155)。

ただし、実際に確保する配列の容量はレコード数と一致するとは限りません。確認した実装では、初期走査の前に「入力ファイルのバイト数 ÷ 32」件分を `reserve()` しています。[容量を予約する箇所](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/parse.cpp#L2813-L2816)。

このため、`12 × 実際の参照数` はレコードのデータ量の目安であり、そのまま確保メモリ量を表す式ではありません。

GlobalId索引やID索引にもハッシュ表などの領域が必要です。全体を見積もるなら、こうした管理領域も足す必要があります。まずは「属性を読まなくても、件数に応じた固定的なコストがある」と押さえておくのがよさそうです。

# 処理時間を考える

## openの時間には全体走査と索引のソートが含まれる

lazy読み込みでも、最初にファイル全体を走査します。したがって、ファイルサイズが大きくなってもopenの時間が一定、という仕組みではありません。

入力サイズを `B`、インスタンス数を `N`、参照数を `R` とすると、主要な処理は次のように整理できます。

| 処理 | 計算量の目安 |
| --- | --- |
| 入力全体の走査 | `O(B)` |
| 属性開始位置のソート | `O(N log N)` |
| 逆参照レコードのソート | `O(R log R)` |
| 未解析インスタンスの位置検索 | 1回あたり `O(log N)` |

これは主要な処理を抜き出した整理です。型別一覧のソートや、ハッシュ表への登録、実際のI/O時間などもあります。

open時に短縮できると考えられるのは、主に属性値の変換や、その格納領域を確保・構築する処理です。一方、属性へ初めてアクセスする際には、位置検索、必要なページの取得、対象インスタンスの属性のパースが発生します。

## 一部だけ使う場合と全件使う場合

一部のインスタンスの属性だけを使って処理が終わるなら、残りの属性をパースせずに済みます。この場合は、パース時間と属性データの保持量を減らせると予想できます。

反対に、全インスタンスの属性を使うなら、後回しにしたパースを最終的にすべて行うことになります。位置検索やページ取得も加わるため、全体の処理時間まで短くなるとは限りません。

同じインスタンスへの2回目以降の属性アクセスでは、保持済みのデータを使います。そのため、最初のアクセスと繰り返しアクセスも分けて見る必要があります。

# 編集や保存ではどうなるか

属性を書き換える処理でも `ensure_loaded()` が呼ばれます。未解析なら、そのインスタンスの属性を読み込んだうえで、保持しているデータを書き換えます。[属性設定時の処理](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/instance_data.h#L630-L643)。

また、STEP形式で保存するときは、各インスタンスの属性を順に取得してテキストへ変換します。未解析のインスタンスでは、この属性取得によって遅延パースが動きます。

```text
保存処理
  インスタンスを順に出力する
    → 属性値を取得する
      → 未解析なら属性一式をパースし、storage_ に保持する
    → 属性値をSTEPテキストにして出力する
```

保存の前に全件をまとめてパースする段階がある、という意味ではなく、出力の過程で順にパースされていく形です。[ファイルの出力ループ](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/parse.cpp#L3797-L3816)、[属性の文字列化](https://github.com/IfcOpenShell/IfcOpenShell/blob/a298d3489419a06636c5f4b423b2fc9c1ceb7c65/src/ifcparse/parse.cpp#L1319-L1354)。

パースした属性は保持されるので、一部の属性しか触っていなくても、ファイル全体を保存する過程でメモリ使用量が増えると考えられます。

# 実測で確かめる

ここまでの説明から、open直後と処理完了時で効果が変わりそうなことが分かりました。実測では、同じ入力ファイルに対して通常読み込みとlazy読み込みを比較します。

:::note warn
この節は測定計画です。以下の表にはまだ実測値を入れていません。
:::

## 測定条件

| 項目 | 条件 |
| --- | --- |
| IfcOpenShellのバージョン・ビルド | 未記入 |
| Python・OS・CPU・搭載メモリ | 未記入 |
| 入力ファイルのサイズ・スキーマ | 未記入 |
| インスタンス数・参照数 | 未記入 |
| 各条件の繰り返し回数 | 未記入 |

インスタンス数や参照数を調べる処理は、性能測定とは別に行います。件数を数えるつもりで属性にアクセスすると、その操作自体が遅延パースを発生させる可能性があるためです。

比較する処理は、それぞれ新しいプロセスで実行します。ある条件でパースした属性が次の条件に残らないようにするためです。ファイルがOSのキャッシュに載っているかどうかでも時間が変わるので、実行順やキャッシュの条件も記録します。

## 比較する操作

| 操作 | 確かめたいこと |
| --- | --- |
| openだけ | 初期走査の時間と、属性未解析時のメモリ |
| 特定の型の一部について属性を取得 | 一部だけ使う場合の効果 |
| 全インスタンスについて全明示属性を取得 | 後回しにしたパースをすべて行う場合のコスト |
| open後、STEP形式で全体を保存 | 保存時のパース時間とメモリの増加 |

属性の取得結果は大きなリストなどに蓄積せず、同じ操作を両方式で行います。また、インスタンス自体の表示は文字列化のために属性を読む可能性があるので、測定中のデバッグ出力にも注意します。

## 結果

時間はopenとその後の処理を分け、両方を含む総時間も記録します。メモリはopen直後と処理終了時のRSSに加え、途中のピークRSSを記録する予定です。

| 操作 | 読み込み方式 | open時間 | open後の処理時間 | 総時間 | open直後のRSS | 終了時のRSS | ピークRSS |
| --- | --- | --- | --- | --- | --- | --- | --- |
| openだけ | 通常 / lazy | 未計測 | ― | 未計測 | 未計測 | 未計測 | 未計測 |
| 一部の属性を取得 | 通常 / lazy | 未計測 | 未計測 | 未計測 | 未計測 | 未計測 | 未計測 |
| 全件の全明示属性を取得 | 通常 / lazy | 未計測 | 未計測 | 未計測 | 未計測 | 未計測 | 未計測 |
| 全体を保存 | 通常 / lazy | 未計測 | 未計測 | 未計測 | 未計測 | 未計測 | 未計測 |

メモリの概算は内部データの一部を積み上げたもので、RSSにはPythonやライブラリ、アロケータなどの領域も含まれます。数値の一致だけでなく、インスタンス数やアクセス範囲を増やしたときの変化も見たいところです。

# おわりに

IfcOpenShell のlazy読み込みは、最初にファイル全体を走査して内部オブジェクトと索引を作り、必要になったインスタンスの属性を後からパースする仕組みでした。

最初から必要な領域と、属性にアクセスするにつれて増える領域があるので、効果はファイルサイズだけでなく、インスタンス数・参照数・実際に使う属性の範囲にも左右されそうです。

「lazyだから軽い」で終わらせず、どこまで処理するのかを決めて測ってみると、使いどころが見えてきそうですね。
